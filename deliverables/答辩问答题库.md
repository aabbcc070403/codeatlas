# CodeAtlas 答辩问答题库（决赛准备）

> 用途：决赛现场答辩（占决赛总分 30%）准备。每题给「答题要点」与「证据出处」；回答口径与技术文档一致，不夸大。特别覆盖赛事要求的「AI 辅助编程须能清晰解释所有代码逻辑」。

## 一、AI 与可信性（最高频）

**Q1. AI 的结论凭什么可信？会不会是编的？**
要点：三层收口——① 只基于工具读到的真实代码判断；② 每条引文逐字符匹配快照真实行段 + 读取覆盖检查；③ 规范引用限定本轮检索白名单。不匹配的候选丢弃并计数（invalidCitations），评测里计入 FP 不美化。可以现场演示「点击引文 → 定位到代码行」。
出处：技术文档 §4.4；`src/core/review/validate.ts`；评测口径 §3。

**Q2. Precision 只有 0.75–0.86，怎么解释？**
要点：如实回答。24 样例小样本口径；v2 提示词（宁缺毋滥）把 FP 从 7–11 条/次压到 0–4 条/次，Recall 9 次运行全部 1.000；剩余 FP 是模型在「相近对照」上的保守性误报。目标 P≥0.80 在 llm_no_rag 列达成（0.857），hybrid 均值贴近；小样本不做外推。
出处：§6.2 表；`deliverables/real-embedding-ablation-2026-09-23.md`。

**Q3. 为什么自研 Agent 循环而不用 LangChain？**
要点：可控性优先于灵活性。四件只读工具 + 三重预算 + 证据校验是硬约束，小状态机比框架钩子更可审计；框架隐藏预算检查点反而增加风险。Agent 仍有规划/工具调用/自主决策（风险优先抽样、循环内自主探索、自主提交）。
出处：§4.1。

**Q4. RAG 到底带来多大提升？**
要点：诚实——对 P/F1 的影响在 n=8 方差内，不宣称显著；稳定增量是**规范引用证据与可解释性**（每条结论可挂规范出处），以及向量+词法双路对短术语文本的召回稳定（29/29 检索真实走 hybrid）。消融设计本身就是加分点（三列对照 + 无效引文计 FP）。
出处：§6.2 如实结论②。

**Q5. 提示词 v1→v2 改了什么？为什么效果这么大？**
要点：v1 允许不确定时降 confidence 提交 → 对照项目被塞进大量「看起来合理」的告警；v2 明确「无确凿证据不提交、空结论是正常结果」→ FP 压到 0–4 条/次且 Recall 不掉。这是同模型同数据集只改提示词的对照实验，是「优化策略」的实证。
出处：§4.3；两轮 deliverables 对照。

## 二、多模态与技术实现

**Q6. 多模态体现在哪？**
要点：追问支持 ≤3 张界面截图（粘贴/上传），图像 part 与代码证据、规范检索在同一上下文融合；预算按固定 token 计图；服务端只存元数据不存原图（隐私取向）。当前实测对话模型为纯文本 DeepSeek，图像链路与 Mock 标注就绪，换 VL 模型（GLM-4V/GPT-4o/Qwen-VL）即获得内容理解——如实说明。
出处：§4.5、README 已知限制 3。

**Q7. 本地嵌入为什么选 bge-small-zh？512 维和 pgvector 固定维度冲突吗？**
要点：中文规范文本、512 维够用且快、ONNX/WASM 本地推理零成本不占日额度、可离线复现；为此做了列维度解耦迁移（vector 不固定维度，按 embedding_model 过滤），换模型跑 `pnpm reindex` 重建。
出处：§4.1/§3.4；迁移 0005。

**Q8. 预算会不会被恶意刷爆？**
要点：三层——单扫描 12/30/6 万+8 千/180s、追问 4/8/60s、全局日额度原子预留（reserve/settle/release 幂等、跨日绑定凭据）；访问码失败限流 10 次/10 分钟；跨会话 404。全部有集成测试（日额度账本 5 项、预算故障矩阵 8 项）。
出处：§4.7。

**Q9. 上传的 ZIP 安全吗？会不会执行我的代码？**
要点：绝不执行上传内容（不跑 npm install / 构建 / 测试 / 仓库自带配置）；导入拒绝路径穿越/绝对路径/盘符/符号链接/保留设备名，按流式解压字节限额；敏感文件（.env/私钥）直接拒绝收录；疑似密钥等长脱敏后再入库/发送。
出处：§3.3 安全边界；README 安全边界。

## 三、工程与测试（含 AI 辅助编程合规）

**Q10. 这些代码都是你们自己写的吗？（AI 辅助编程合规）**
要点：如实回答——开发大规模使用 AI 辅助编程 + 人工逐项审阅，符合赛事规则；**每段代码逻辑我们都能解释**（可现场指任何模块讲解：如预算包装、证据校验、租约恢复）；344 项测试 + 架构文档保证可讲清；Git 提交历史是真实开发记录。建议答辩前把 README「开发方式说明」段落熟读。
出处：README 开发方式说明；`docs/architecture.md`。

**Q11. 344 项测试都测了什么？会不会是刷数字？**
要点：三层分工——单元 204（规则/脱敏/预算/指标手算/对比语义/语料契约，纯函数断言）、集成 131（真实库上全流程 + 租约恢复 + 日额度账本 + 评测台账 + 注入防线）、E2E 9（生产构建闭环 + 移动端无溢出 + UI 回归）。指标定义有 18 项手算表测试对齐，杜绝实现和口径漂移。
出处：§6.1；`tests/` 目录结构。

**Q12. Git 历史为什么前期是一个大提交？**
要点：如实回答——前期以整机基线交付，后期按功能细粒度提交（修复/新增/重构/测量分类，不倒填不伪造）；这是 AI 辅助高速开发的真实痕迹。评审如需，可按提交讲解每个功能的改动面。
出处：README 开发方式说明。

**Q13. Docker 部署验证过吗？**
要点：如实——Compose 与 Dockerfile 已实现并人工审阅（多阶段构建/非 root/fixtures 随镜像/密钥强制注入），本机无 Docker 未实测，列为首次部署验证项；本地路径（PGlite）全量验证过，生产 PG 有直连集成测试机制。诚实是产品主张的一部分。
出处：§6.4、README 已知限制 4/5。

## 四、产品与商业

**Q14. 和 Copilot / SonarQube / 通义灵码比？**
要点：它们面向「写代码提效」或「企业流水线」；我们面向「提交前自查自证」——差异在证据闭环（引文硬校验）、诚实语义（未再检出≠已验证修复）、学生成本（本地嵌入零成本）。见 §7.3 差异表。

**Q15. 怎么赚钱？社会价值是什么？**
要点：教育版 SaaS 订阅 / 院校私有化采购（Docker Compose 即交付）/ 竞赛冲刺增值服务；社会价值：把企业级「证据可核验」能力带到高校，降低初次工程实践质量风险，是「负责任 AI」的教学案例。见 §7.4。

**Q16. 未来规划？**
要点：MCP 工具集成进 IDE、浏览器端 WebGPU 轻量初筛（端云协同）、评测扩容与更强模型对照、团队协作与误报回流。见 §8.3。
